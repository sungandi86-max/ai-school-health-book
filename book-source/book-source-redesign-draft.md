# 『보건교사의 일을 시스템으로 바꾸는 법』

## 부제 초안

반복을 발견하고, 업무를 구조화하고, 나만의 도구로 발전시키는 실전 기록

> 이 문서는 리디자인 첫 통합 초안이다. 앱 기능에 관한 사실은 2026-09-30 현재 로컬 저장소의 코드·화면·schema를 기준으로 썼다. 실제 학교 경험은 2026-10-01까지 확인한 저자 인터뷰를 반영했다. BOGUNON DESK Chapter 21의 실사용 검증은 기능 동결 후 작성한다. 모든 출판 화면은 mock 데이터로 다시 캡처한다.

## PART 1. 바쁜 하루를 업무 문제로 발견하다

### Chapter 01. 바쁜 하루에서 멈춘 장면 하나 찾기

보건실의 하루는 한 가지 일로 이어지지 않습니다. 학생을 살피다가 전화를 받고, 안내를 보내다가 응급처치를 하고, 다시 컴퓨터 앞에 앉았을 때는 어느 파일을 열었는지부터 찾아야 합니다. 하루 종일 움직였는데 아침에 열어 둔 파일은 그대로일 때도 있습니다.

이 장면을 개인의 집중력 문제로만 보면 해법은 “더 잘 기억하기”가 됩니다. 그러나 실제로 줄여야 할 것은 학생을 돌보는 시간이 아닙니다. 중단된 뒤 원래 자리로 돌아가기 위해 파일을 찾고, 앞서 한 판단을 떠올리고, 같은 정보를 다시 적는 시간입니다.

첫 단계는 거창한 자동화가 아니라 멈춘 장면 하나를 기록하는 일입니다. 업무 이름 대신 손이 한 행동을 적습니다.

| 기록할 것 | 질문 |
|---|---|
| 하던 일 | 중단되기 전 무엇을 하고 있었나? |
| 들어온 일 | 누가 무엇을 요청했나? |
| 돌아오기 | 원래 일을 다시 시작하려고 무엇을 찾았나? |
| 반복 | 다시 쓰거나 다시 설명한 정보는 무엇인가? |
| 판단 | 끝까지 사람이 확인해야 한 것은 무엇인가? |

온라인 보건실, 별도검사 도우미, BOGUNON, BOGUNON DESK도 기능 목록에서 시작하지 않습니다. 이 책에서는 네 시스템을 “무엇을 만들었는가”보다 “어느 반복을 발견했고 어떤 구조로 바꾸었는가”의 증거로 사용합니다.

#### 실습 01. 오늘 멈춘 장면 한 개

- 학생·교직원 실명과 건강정보는 적지 않습니다.
- 중단 전 행동, 끼어든 요청, 다시 시작할 때 찾은 것을 한 줄씩 적습니다.
- 없애면 안 되는 돌봄·판단과 줄일 수 있는 재탐색·재입력을 나눕니다.

**이 장의 결과물:** 하루 한 장면 해부표 1장

### Chapter 02. 반복되는 일을 업무 지도로 바꾸기

“건강검진 업무가 많다”는 말만으로는 바꿀 지점을 찾기 어렵습니다. 큰 업무명 아래에는 자료를 찾고, 이름을 옮기고, 기한을 알리고, 제출 여부를 확인하고, 다시 설명하는 작은 행동이 숨어 있습니다.

반복은 다음 다섯 가지에서 자주 발견됩니다.

1. 다시 찾기: 파일, 링크, 연락처, 이전 기록을 찾습니다.
2. 다시 쓰기: 같은 날짜·대상·상태를 여러 곳에 적습니다.
3. 다시 보내기: 이미 전달한 안내를 사람마다 반복합니다.
4. 다시 확인하기: 누가 했고 누가 남았는지 여러 표를 대조합니다.
5. 다시 설명하기: 기준 위치가 없어 같은 질문에 답합니다.

| 관찰한 장면 | 반복 행동 | 필요한 변화의 방향 |
|---|---|---|
| 제출 여부를 여러 번 묻는다 | 다시 확인·설명 | 제출 상태를 확인할 한 위치 |
| 별도검사 당일 명단을 여러 사람이 본다 | 다시 찾기·전달 | 현재 흐름과 예외를 함께 보는 상태 |
| 행사 준비물을 메모와 파일에서 찾는다 | 다시 찾기·쓰기 | 행사 한 건과 체크리스트 연결 |
| PC에서 앱·폴더·메모를 계속 연다 | 다시 찾기·옮기기 | 업무를 시작할 한 환경 |

이때 “앱이 필요하다”를 아직 결론으로 쓰지 않습니다. 먼저 반복 행동과 완료 기준을 적습니다. 앱은 그 구조를 실제 운영으로 옮길 때 필요한 여러 선택지 중 하나입니다.

#### 실습 02. 반복 업무 지도

최근 일주일의 반복 장면 세 개를 고릅니다. 각 장면에 `찾기/쓰기/보내기/확인/설명`을 표시하고, 그 반복이 끝났다고 판단할 수 있는 상태를 한 줄로 적습니다.

**이 장의 결과물:** 반복 장면 기록지와 반복 업무 지도

## PART 2. 바꿀 일과 남길 일을 정하다

### Chapter 03. 가장 작게 끝까지 시험할 업무 고르기

처음부터 보건실 전체를 바꾸려 하면 무엇이 좋아졌고 어디에서 멈췄는지 확인하기 어렵습니다. 좋은 첫 과제는 가장 큰 문제가 아니라 시작부터 끝까지 따라갈 수 있는 문제입니다.

첫 과제는 네 기준으로 고릅니다.

| 기준 | 확인 질문 |
|---|---|
| 반복성 | 같은 행동이 다시 생기는가? |
| 범위 | 한 명의 사용자와 한 개 흐름으로 줄일 수 있는가? |
| 위험 | 건강 판단과 개인정보를 제외해도 시험할 수 있는가? |
| 검증 | 성공과 실패를 화면이나 기록으로 확인할 수 있는가? |

“온라인 보건실을 만든다”는 너무 큽니다. “교직원이 한 안내를 찾아 읽고, 필요한 제출 위치로 이동하고, 자기 제출 상태를 확인한다”는 끝까지 따라갈 수 있습니다. “별도검사를 디지털화한다”보다 “한 학급이 대기에서 진행 중으로 바뀌고 다음 담당자가 그 변화를 본다”가 검증하기 쉽습니다.

#### CASE. 범위를 한 문장으로 고정하기

> 이 과제는 **누가** **어떤 상황에서** **무엇을 끝내도록** 돕고, 이번에는 **무엇을 하지 않는다**.

예: 이 과제는 교직원이 가상 이수증의 제출 위치와 자기 상태를 확인하도록 돕고, 실제 개인정보가 든 파일 업로드는 연습에서 다루지 않는다.

#### 실습 03. 첫 개선 과제 선정표

후보 세 개를 반복성·위험·검증 가능성으로 비교한 뒤 한 개만 선택합니다. 제외한 범위도 함께 적습니다.

**이 장의 결과물:** 첫 과제 한 문장과 제외 목록

### Chapter 04. 사람의 판단과 개인정보 경계 남기기

자동화의 시작은 더 많은 일을 맡기는 것이 아니라 끝까지 사람이 맡을 일을 정하는 것입니다. 학생의 상태를 해석하고, 상담 내용을 판단하고, 예외의 사유를 살피는 일은 화면의 상태값만으로 끝내면 안 됩니다.

| 구역 | 예시 | 원칙 |
|---|---|---|
| 사람이 판단 | 응급성, 상담, 개별 조치, 예외 승인 | 사람이 원문과 맥락을 확인한다. |
| 시스템이 보조 | 기한 표시, 상태 집계, 정해진 문장 정리 | 확정된 정보만 다룬다. |
| 공개 가능 | 일반 안내, 가상 일정, 공통 준비물 | 공개 범위를 먼저 정한다. |
| 내부 관리 | 제출 상태, 담당자, 운영 메모 | 역할별 접근을 나눈다. |
| 입력·공개 금지 | 실제 건강정보, 상담내용, 주민번호, 개인 연락처 | 출판·AI 입력·공개 화면에서 제외한다. |

온라인 보건실 코드에는 일반 교직원, 담임, 보건교사, 관리자의 역할이 나뉘어 있습니다. 별도검사 도우미에도 역할별 화면이 있지만 인증과 세부 권한 강제는 아직 완성 범위가 아닙니다. BOGUNON은 사용자 범위의 데이터 정책을 위한 migration을 갖고 있고, BOGUNON DESK는 로컬 파일 처리와 Windows DPAPI로 보호하는 세션 구조를 둡니다. “권한 기능이 있다”와 “모든 운영 환경에서 보안 검증이 끝났다”는 같은 말이 아닙니다.

#### 실습 04. 사람·보조·금지 경계표

자기 업무 한 건을 세 칸으로 나눕니다.

- 사람이 끝까지 판단할 것
- 정해진 기준으로 보조받을 것
- 외부 입력·공개 화면에 올리지 않을 것

**이 장의 결과물:** 사람·시스템·정보 경계표

## PART 3. 화면보다 먼저 업무를 설계하다

> ### 브리지. 이제 화면이 아니라 업무 설계도를 만듭니다
>
> PART 1에서는 멈춘 장면과 반복을 찾았습니다. PART 2에서는 바꿀 범위와 남길 판단을 정했습니다. 이제 버튼과 색을 고르기 전에 업무의 시작, 상태, 정보, 다음 행동을 종이 위에 놓습니다. 이 설계도가 있어야 화면이 바뀌어도 업무의 기준은 남습니다.

### Chapter 05. 큰 업무를 동사로 나누기

건강검진, 보건교육, 행사 보건지원은 모두 명사입니다. 명사만 적으면 누가 무엇을 하고 언제 끝나는지가 보이지 않습니다. 그래서 실제 손의 움직임을 동사로 바꿉니다.

예를 들어 “행사 보건지원”은 다음처럼 나눌 수 있습니다.

`요청을 받는다 → 날짜와 장소를 확인한다 → 예상 인원을 적는다 → 준비물을 고른다 → 확보 방법을 정한다 → 완료를 표시한다 → 행사 후 메모를 남긴다`

현재 BOGUNON의 행사 보건지원 데이터도 행사 정보와 준비물 체크리스트를 나눕니다. 이 구조는 기능을 많이 만들기 위한 것이 아니라, 준비가 끝났다는 기준을 보이게 하기 위한 것입니다.

| 동사 | 시작 조건 | 남길 정보 | 다음 행동 |
|---|---|---|---|
| 요청받기 | 행사 요청 도착 | 유형·날짜·장소 | 범위 확인 |
| 준비하기 | 범위 확정 | 준비물·수량·확보 방식 | 완료 표시 |
| 운영하기 | 행사일 도착 | 필요한 운영 기록 | 사후 메모 |

#### 실습 05. 명사를 5~10개의 동사로

업무 한 개를 고르고 실제 순서대로 동사를 적습니다. “관리한다”, “확인한다”처럼 넓은 말은 무엇을 보고 무엇을 바꾸는지 다시 씁니다.

### Chapter 06. 대기·확인·완료의 기준 정하기

상태는 색 이름이 아니라 다음 행동을 정하는 약속입니다. “확인 중”이라고 썼다면 무엇을 확인하면 끝나는지, 누가 다음 상태로 바꾸는지가 있어야 합니다.

별도검사 도우미의 현재 구현은 하나의 여섯 단계 상태표가 아닙니다. 대상을 나눠 서로 다른 상태를 둡니다.

| 대상 | 실제 구현 상태·값 | 의미 |
|---|---|---|
| 학급 운영 | 대기, 진행 중, 완료, 미도착 | 학급 단위의 현재 흐름 |
| 운영 지연 | 지연 분 값 | 예정과 실제 흐름의 차이 |
| 학생 | 대기, 완료, 결석, 조퇴, 지각, 추후검진 | 개인별 예외와 결과 |
| 화면 표현 | 확인 필요 | 일부 예외를 사람이 다시 보도록 묶는 표시 |

현장에서 “이동”, “검사 중”, “지연”, “확인 필요”라는 말을 사용하더라도 저장 구조는 목적에 따라 다릅니다. 이동은 안내와 운영 단계로 나타나며 하나의 공통 저장 상태로 확인되지 않습니다. 책에서는 보기 좋은 여섯 칸을 만들기보다 왜 학급과 학생의 상태를 나눴는지 설명합니다.

|---|---|---|---|---|
|  |  |  |  |  |

“확인했다” 대신 확인한 대상과 바뀐 값을 적습니다.

**이 장의 결과물:** 행동·상태 기준표

### Chapter 07. 행과 열로 업무 설계도 만들기

표의 한 행은 업무 한 건이어야 합니다. 한 열은 다음 행동을 결정하는 데 필요한 정보여야 합니다. 쓸 수 있다는 이유만으로 열을 늘리면 입력 부담과 개인정보 위험도 함께 늘어납니다.

| 설계 질문 | 예시 |
|---|---|
| 한 건은 무엇인가? | 행사 한 건, 검사 세션 한 건, 제출 항목 한 건 |
| 누가 시작하는가? | 보건교사, 교직원, 관리자 |
| 현재 상태는 무엇인가? | 계획, 진행, 회신 대기, 완료 |
| 다음 행동은 무엇인가? | 준비물 확보, 보완 요청, 학급 이동 안내 |
| 꼭 필요한 정보는 무엇인가? | 날짜·대상·담당·상태 |
| 빼야 할 정보는 무엇인가? | 목적과 무관한 건강정보·개인 연락처 |

실제 자료를 넣기 전에 세 건의 mock 데이터로 시험합니다. 정상 한 건, 지연 한 건, 확인이 필요한 한 건을 만들면 열과 상태가 다음 행동을 충분히 설명하는지 볼 수 있습니다.

#### 실습 07. 업무 설계표와 mock 세 건

업무 한 건의 단위를 정하고 각 필드의 존재 이유를 적습니다. 이유를 설명할 수 없는 열은 보류합니다. 가상 값 세 건으로 정상과 예외를 따라갑니다.

**이 장의 결과물:** 업무 설계표와 첫 mock 데이터

## PART 4. 첫 시스템, 온라인 보건실을 운영하다

### Chapter 08. 화면부터 만들고 실패한 이유

화면이 열리고 메뉴가 보이면 완성에 가까워졌다고 느끼기 쉽습니다. 그러나 업무 시스템은 첫 화면이 아니라 마지막 행동에서 확인됩니다. 안내를 읽은 교직원이 어디로 이동하는지, 제출 뒤 자기 상태를 볼 수 있는지, 보건교사가 보완 대상을 구분할 수 있는지가 이어져야 합니다.

학교에서 외부 강사의 ‘온라인 교무실’ 교직원 연수를 들었습니다. 보건실도 이런 방식으로 운영하면 좋겠다고 생각했고, 직접 첫 화면을 구현했습니다. 처음에는 내가 화면을 만들었다는 사실 자체가 신기해 완성된 것처럼 느껴졌습니다.

시간을 두고 다시 보니 첫 화면은 보건실의 업무를 끝내는 시스템보다 일반적인 웹페이지에 가까웠습니다. 교직원이 필요한 업무로 들어가기 어려웠고, 기존에 사용하던 Google Sheets와 연결하는 과정에서도 원했던 메뉴와 흐름이 제대로 이어지지 않았습니다.

여기서 처음 확인한 실패는 화면의 완성도와 업무의 완성도가 다르다는 사실이었습니다.

> **내가 보기 좋은 화면과 교직원이 쓰기 좋은 화면은 달랐습니다.**

현재 저장소에는 기존 포털 route와 Firebase v2 route가 함께 있습니다. 이것은 현재 전환 상태를 보여주는 기술적 사실입니다. 왜 두 구조가 공존하게 되었는지, 어느 화면을 실제 학교에서 사용했는지는 코드만으로 판단하지 않습니다.

#### Before / After

| 화면부터 시작 | 업무부터 시작 |
|---|---|
| 메뉴 이름을 먼저 정한다 | 사용자가 끝내려는 일을 먼저 적는다 |
| 정보 카드를 채운다 | 시작·상태·완료 위치를 잇는다 |
| 첫 화면이 열리면 성공으로 본다 | 다른 계정으로 끝까지 따라가 본다 |

#### 실습 08. 완성처럼 보인 근거 분리

만든 화면에서 “보인다”와 “업무를 끝낼 수 있다”를 두 칸으로 나눕니다. 실제로 눌러 끝까지 확인한 경로만 두 번째 칸에 적습니다.

### Chapter 10. 제출·검진·교육·담임 협조를 하나의 동선으로 잇기

포털의 카드는 서로 떨어진 안내판이 아닙니다. 사용자는 홈에 들어와 필요한 정보를 확인하고, 제출하거나 협조하고, 처리 상태를 다시 확인합니다. 보건교사는 그 뒤에서 제출 현황과 확인 대상을 봅니다.

현재 코드에는 심폐소생술 연수 이수증, 개별 건강검진 확인, 채용검진 대체통보서 요청, 감염병 보고와 나의 제출 현황을 위한 화면이 있습니다. 이 목록은 구현된 제출 유형을 보여주지만, 실제 자료를 출판 화면에 써도 된다는 뜻은 아닙니다. 캡처에는 가상 이수증과 가상 사용자만 사용합니다.

`진입 → 대상·기한 확인 → 제출 또는 요청 → 자기 상태 확인 → 보건교사 확인 → 필요 시 보완`

이 동선에서 한 단계라도 다른 메시지나 파일에 의존하면 다시 찾기가 생깁니다. 그래서 각 화면의 완료 기준을 정하고 다른 계정으로 같은 경로를 확인합니다.

### Chapter 11. 실제 학교에서 사용하고 고치기

시스템은 공개한 날보다 사용자가 멈춘 자리에서 더 많이 배웁니다. 다만 저장소는 화면과 변경 이력을 보여줄 뿐, 실제 학교에서 누가 어디에서 멈췄고 무엇이 달라졌는지는 증명하지 않습니다.

첫 실제 사용자는 담임교사였습니다. 처음 사용한 업무는 월별 보건실 입실 현황 확인이었습니다. 학생 개인정보는 마스킹하고 질병명은 공개하지 않았지만 학교 내부 정보였기 때문에 학년별 비밀번호를 설정했습니다.

비밀번호는 접근을 제한하는 가장 빠른 방법이었지만, 매년 학년별 비밀번호를 다시 바꿔야 했습니다. 접근을 편하게 만들기 위해 만든 구조가 보건교사에게 또 하나의 반복 업무가 된 것입니다.

이후 Firebase를 연결하고 교직원 로그인 방식을 도입했습니다. 학교에서 사용하는 Microsoft Teams 계정을 기반으로, 교직원이 별도로 가입하지 않고 학교 계정으로 접근하게 했습니다. 학기별로 권한을 부여해 권한이 있는 사람만 필요한 정보에 접근하도록 구조를 바꿨습니다.

비밀번호를 기억하고 매년 다시 배포하는 방식에서, 학교 계정과 학기별 권한을 확인하는 방식으로 운영 기준이 바뀌었습니다. 다만 Apps Script 버전의 기능이 Firebase v2로 완전히 이전되지는 않아 일부 흐름은 아직 매끄럽지 않습니다.

현재 코드에서 확인되는 최근 변화에는 완료 제출 숨김, 교직원 식별자 자동 연결, 관리자 대시보드 계층 개선이 있습니다. 이것을 실제 사용자 반응의 결과라고 단정하지 않고, 변경 이력의 예로만 다룹니다.

## PART 5. 명단이 아니라 흐름을 관리하다: 별도검사 도우미

### Chapter 12. 명단을 여러 운영 상태로 바꾸기

별도검사 당일에는 명단이 있어도 지금 어느 학급이 기다리는지, 어느 학급을 안내해야 하는지, 누가 예외로 남았는지 즉시 알기 어렵습니다. 문제는 명단의 존재가 아니라 흐름의 위치입니다.

현재 구현은 대기·이동·검사중·완료·지연·확인필요를 하나의 열에 넣지 않습니다. 학급, 운영, 학생을 나눕니다.

- 학급: 대기, 진행 중, 완료, 미도착
- 지연: 분 단위 값
- 학생: 대기, 완료, 결석, 조퇴, 지각, 추후검진
- 확인 필요: 일부 예외를 사람이 다시 보게 하는 UI 표현
- 이동: 현재 학급에 대한 안내와 운영 단계로 표현

이 분리는 같은 색을 늘리는 대신 누가 다음 행동을 해야 하는지를 분명하게 합니다. 학급이 진행 중이어도 학생 한 명은 추후검진일 수 있습니다. 지연은 학생의 건강상태가 아니라 운영 시간의 차이입니다.

### Chapter 13. 교사용·관리자·가로 현황판을 하나의 운영으로 연결하기

화면은 역할에 따라 달라도 같은 운영 사실을 가리켜야 합니다. 현재 저장소에는 운영 센터, 교사용 화면, 관리자 화면, 가로형 현황판 component가 각각 존재합니다.

| 역할 | 주로 볼 것 | 다음 행동 |
|---|---|---|
| 현장 교사 | 현재 학급과 이동 안내 | 학급 안내·현장 확인 |
| 관리자 | 전체 진행률, 현재 학급, 지연 | 흐름 조정·예외 확인 |
| 표시 화면 | 개인정보 없는 공통 진행 정보 | 공동 상황 인식 |
| 보건교사 | 세션·조건·대상·운영 전체 | 준비·운영·마감 |

접근 행렬과 역할별 화면은 구현돼 있지만 최종 인증, QR 토큰 검증, RLS까지 모두 끝난 것은 아닙니다. 그러므로 책에서는 화면 역할을 설명하되 보안이 완성됐다고 쓰지 않습니다.

## PART 6. 반복만 AI에 맡기다

### Chapter 15. 같은 정보를 다시 적는 자리 없애기

AI를 붙이기 전에 같은 사실을 몇 번 적는지 봅니다. 일정의 날짜를 캘린더, 업무 목록, 안내문에 각각 입력하고 있다면 문장을 빨리 쓰는 도구보다 최초 기록 위치가 먼저 필요합니다.

`같은 정보를 다시 적지 않기`의 핵심은 모든 것을 한 표에 넣는 것이 아닙니다. 한 번 확정된 사실을 기준 위치에 기록하고, 다음 단계에서는 새로 생긴 사실만 더하는 것입니다.

| 정보 | 최초 기록 위치 | 다음 단계에서 추가할 것 | 다시 쓰지 않을 것 |
|---|---|---|---|
| 검진 일정 | 일정 한 건 | 대상·준비 상태 | 같은 날짜 |
| 제출 항목 | 제출 정의 | 개인별 제출 상태 | 항목명·기한 |
| 검사 세션 | 세션 설정 | 학급 흐름·예외 | 검사명·기본 조건 |
| 행사 | 행사 보건지원 | 준비물 확보·완료 | 날짜·장소·담당 |

온라인 보건실의 제출 정의와 제출 상태, 별도검사 도우미의 세션과 운영 상태, BOGUNON의 행사와 체크리스트는 각각 기준 정보와 변화하는 정보를 나누는 예입니다. 실제 앱 사이에 확인되지 않은 자동 연동이 있다고 쓰지는 않습니다.

#### Workflow. 반복 입력 줄이기

1. 같은 정보가 등장하는 위치를 표시합니다.
2. 그 정보가 처음 확정되는 위치를 고릅니다.
3. 다음 단계에서 새로 생기는 정보만 적습니다.
4. 두 화면이 같은 기준을 보는지 확인합니다.
5. 어긋났을 때 고칠 책임 위치를 정합니다.

#### 실습 15. 중복 제거표

업무명, 날짜, 대상, 담당, 상태를 반복 입력하는 위치를 찾습니다. 각 정보의 최초 기록 위치와 다음 단계에서 새로 더할 값만 남깁니다.

**이 장의 결과물:** 중복 제거표와 정보 기준 위치

AI에게 맡길 것은 아직 결정되지 않은 판단이 아닙니다. 사람이 대상과 기한, 공개 범위와 최종 조치를 먼저 확정한 뒤 반복해서 다듬는 한 칸만 보조받습니다.

### Chapter 18. 실제 업무 문제를 BOGUNON 기능으로 바꾸기

기능은 아이디어 목록이 아니라 반복 행동에 답해야 합니다. 현재 코드에서 확인되는 네 영역을 문제→행동→데이터→다음 행동으로 읽으면 다음과 같습니다.

#### 일정

- 문제: 날짜를 확인한 뒤 관련 업무를 다시 찾아야 한다.
- 필요한 행동: 월·주·일의 일정과 학교 날짜 기록을 확인한다.
- 실제 기능: `/calendar`의 월·주·일 보기, 일정·업무·학교 날짜 기록.
- 다음 행동: 예정된 업무를 열고 상태를 갱신한다.

#### 업무

- 문제: 할 일을 적어도 회신 대기와 재확인 시점을 구분하기 어렵다.
- 필요한 행동: 분류·반복·상태·검색 기준으로 다음 일을 찾는다.
- 실제 기능: `/tasks`; 계획, 진행 중, 회신 대기, 확인 필요, 완료, 보류 상태.
- 다음 행동: 현재 상태에 맞는 확인 또는 완료를 기록한다.

#### 행사 보건지원

- 문제: 행사 정보와 준비물 확보 상태가 떨어져 있다.
- 필요한 행동: 행사 한 건에 날짜·장소·인원·담당과 준비물 체크리스트를 연결한다.
- 실제 기능: 체육대회·수련활동·현장체험학습·수학여행·기타 유형, 계획·진행·완료·사후 메모, 준비물 수량·확보 방법·완료 표시.
- 다음 행동: 남은 준비물을 확인하고 행사 후 기록을 남긴다.

#### 교직원 연락처

### Chapter 19. BOGUNON을 실제 업무에 사용하고 고치기

실제 사용에서 가장 자주 쓰는 기능은 일정관리입니다. 연간계획과 실제 실무일정을 연결하는 기능도 예상보다 유용했습니다. 연간계획이 문서에만 머무르지 않고 실제 일정으로 이어질 때 계획은 운영의 기준이 됩니다.

대표 사례는 보건지원강사 관리입니다. 기능을 새로 추가하려고 살펴보면 이미 Google Sheets나 웹앱으로 잘 사용하고 있는 경우가 많았습니다. 이런 도구를 모두 다시 만드는 대신 BOGUNON 안에서 연결해 사용하고 있습니다.

현재까지 이 방식은 실제 업무에 사용하고 있습니다. 다만 연락처 영역은 아직 덜 다듬어졌습니다. 확인되지 않은 시간 절감 수치나 효과를 붙이지 않고, 잘 쓰고 있는 도구를 다시 찾지 않아도 되도록 연결했다는 변화까지만 기록합니다.

> **통합은 모든 것을 새로 만드는 일이 아니라 이미 잘 쓰고 있는 도구를 다시 찾지 않아도 되게 연결하는 일이었습니다.**

현재 저장소의 최근 커밋에는 행사 보건지원, 교직원 연락처, 업무 상태 수정이 포함돼 있습니다. 이를 사용자 피드백의 결과라고 추정하지 않고 실제 변경 근거로만 기록합니다.

### Chapter 20. BOGUNON DESK가 시작된 Windows 업무환경 문제

업무를 구조화한 뒤에도 Windows에서는 폴더를 찾아 파일을 열고 공문을 확인하는 행동이 반복됐습니다. 특히 품의를 올릴 때마다 개요와 품목을 다시 입력하는 일이 번거로웠습니다. DESK에서 가장 먼저 해결하고 싶었던 일은 공문과 품의를 더 쉽게 작성하는 것이었습니다.

BOGUNON에 이미 있는 기능은 DESK에 다시 만들지 않고 연결해 사용하려 했습니다. kimju 선생님의 TD2 바탕화면형 업무환경을 참고하되, 교과교사에게만 필요한 기능은 제외하고 보건교사에게 필요한 기능을 중심으로 구성했습니다.

웹앱은 사용할 때마다 실행하거나 브라우저로 들어가야 합니다. DESK는 Windows가 시작될 때 자동으로 실행되어 PC를 켜면 바로 업무를 시작할 수 있는 환경을 목표로 했습니다.

> **BOGUNON이 업무를 모으는 시스템이라면, DESK는 그 업무를 매일 시작하는 작업환경입니다.**

> **DESK는 기능을 늘리는 앱이 아니라 업무를 시작하기까지의 동작을 줄이는 앱입니다.**

현재 main은 Tauri 2, React, TypeScript, Rust로 구성된 Windows 앱이며 `DashboardCanvas`가 실제 진입 화면입니다. 과거 mock 레이아웃은 현재 화면으로 사용하지 않습니다. 12열 기반 위젯 작업공간과 편집 가능한 Dock, 명령 팔레트와 검색이 존재합니다.

## 에필로그. 반복은 줄이고, 판단은 남기다

보건실의 일은 계속 바뀝니다. 학교 일정이 바뀌고, 담당자가 바뀌고, 새로운 학생과 새로운 상황을 만납니다. 그래서 완성된 도구 하나보다 중요한 것은 업무를 다시 보고 고칠 수 있는 기준입니다.

온라인 보건실은 반복 안내와 제출의 입구를 업무 목적에 따라 나누는 법을 보여주었습니다. 별도검사 도우미는 명단을 보는 일과 흐름을 운영하는 일이 다르다는 것을 보여주었습니다. BOGUNON은 흩어진 일정·업무·행사 준비·연락처를 각각의 다음 행동으로 연결하는 구조를 보여줍니다. BOGUNON DESK는 현재 구현된 Windows 업무환경이 이 구조를 어떻게 일상의 시작점으로 확장하는지 보여줍니다. 아직 확인되지 않은 경험과 개발 중인 범위는 완성된 사실처럼 채우지 않았습니다.

AI는 이 과정의 주인공이 아닙니다. 사람이 문제를 발견하고 경계를 정하고 상태를 설계한 뒤, 판단이 끝난 반복을 정리하는 작은 보조 역할을 맡습니다. 학생을 돌보고 예외를 판단하고 마지막으로 승인하는 책임은 사람에게 남습니다.

책을 덮은 뒤 처음으로 돌아가 봅니다. 오늘 업무에서 멈춘 장면 하나는 무엇이었습니까? 그 장면에서 학생을 돌보는 일은 그대로 두고, 다시 찾고 다시 쓰고 다시 설명한 일 하나만 줄일 수 있다면 어디에서 시작하시겠습니까?
